# 电视端导航与界面设计（第 0 步 + 第 1 步）

日期：2026-08-30

## 背景

KVideo 通过 `android-tv/` 的 WebView 壳运行在 Android TV 上。在电视上，遥控器方向键是唯一的导航输入，但 **Android WebView 默认不启用空间导航**（Chrome 需要 `--enable-spatial-navigation`，WebView 没有对应开关）。

后果：方向键只会滚动页面，焦点永远不会移动到任何控件上。网页里**没有任何一个按钮是可以被选中并按下的**。

已观察到的具体表现：

- 首页的「电影 / 电视剧」切换、「为你推荐」等分类标签都无法选中
- 页面能滚动，但滚不回最顶部
- 播放器的选集、换源、收藏按钮全部不可达
- sticky 顶栏（`z-[2000]`）会盖住其下方的「电影 / 电视剧」按钮，加重了问题

播放页此前通过「在电视上自动进入窗口全屏」绕开了这个问题（见 `useIsTvLike`），但那只解决了单点，没有解决导航本身。

## 设备实测数据

在用户的 Android TV 上通过临时诊断浮层测得：

```
tv=Y bridge=N androidUA=Y 960x540 dpr=2 touch=0 fs=window
```

- **CSS 视口 960×540**，`devicePixelRatio = 2`，即实际渲染画布为 1920×1080 物理像素。面板是 4K，但 Android TV 系统 UI 以 1080p 渲染后由硬件放大——网页侧无法要求更大的画布。
- **布局必须按 960 CSS px 宽度设计**，不是 1920。
- `window.KVideoAndroid` 不存在：设备上安装的 APK 早于该 JS 桥的引入，因此任何依赖它的判定都恒假。
- `maxTouchPoints === 0`，该设备如实报告无触摸。

## 目标

1. 遥控器方向键可以在电视上的所有交互元素之间移动焦点，Enter 可以激活
2. 首页改为电视布局：每个分类一行横向卡片，上下换分类、左右挑片

## 非目标

- **不改动手机端和桌面端的任何行为或样式**（用户明确要求）
- 不改动 `android-tv/` 里的任何 Android 代码
- 本设计不覆盖播放页、搜索页、收藏页——它们是后续独立步骤

## 约束

- 所有电视端代码路径必须由 `useIsTvLike()` 把守，手机端不得进入
- 部署在 Cloudflare Pages，所有 API 路由为 edge runtime
- 豆瓣接口在境外部署上不稳定（上游有「境外部署海报大量 500」的历史修复），不能一次并发拉取全部分类

## 架构决策

### 决策一：独立的 TV 组件树，共用数据层

页面顶层根据 `isTvLike` 决定渲染电视组件还是现有组件：

```tsx
// app/page.tsx
if (isTvLike) return <TvHome />;
return <ExistingHome />;
```

数据 hook（豆瓣推荐、收藏、播放历史）完全复用，只有展示层是两套。

**为什么不在现有组件上加电视样式**：现有首页是网格结构，无法改成行式布局；而且需要在每个组件内部散布 `isTvLike` 判断，正是最容易误伤手机端的做法。

**为什么不做独立的 `/tv` 路由**：隔离收益已由上述方案取得，但要重写数据获取，且 Android 壳加载的是固定 URL，还需处理重定向。

### 决策二：模型导航，不做几何计算

通用空间导航「找某方向上几何最近的可聚焦元素」在电视上经常跳到视觉相近但逻辑无关的元素。既然布局是规整的行 × 列结构，直接维护 `(行号, 列号)`：

- **左 / 右**：行内移动，到头停住（不循环、不跳行）
- **上 / 下**：跳到上 / 下一个非空行，保持列号；目标行更短则取该行最后一个
- **空行跳过**（分类尚未加载时）
- **到顶 / 到底停住**：顶栏本身就是第 0 行，由上述规则自然处理，不需要特例

行为完全确定，没有意外跳转。

### 决策三：用真实 DOM 焦点

导航模型只负责决定该聚焦哪个元素，然后调用 `element.focus()`。其余交给浏览器：

- Enter 激活是原生行为（聚焦的 `<button>` 按 Enter 自动触发 click），不需要自建激活分发
- `:focus-visible` 样式天然可用
- 不破坏无障碍语义

每个可聚焦项是真实的 `<button>`，`tabIndex={-1}`（不进入 Tab 序列，只由导航引擎控制）。

## 第 0 步：导航内核

| 文件 | 职责 |
|---|---|
| `lib/tv/focus-model.ts` | 纯函数 `moveFocus(rows, current, direction)` → 新坐标。不接触 DOM |
| `lib/tv/TvFocusProvider.tsx` | 行注册表 + 当前坐标；行组件通过 `useTvRow(id)` 注册元素 ref |
| `lib/tv/useTvKeys.ts` | 全局 keydown → 调用模型 → `focus()` + `scrollIntoView` |
| `app/styles/tv.css` | 焦点环、放大动效、`scroll-margin-top` |

### 数据结构

```ts
type Direction = 'up' | 'down' | 'left' | 'right';
interface TvRowMeta { id: string; length: number; }
// rowIndex 是 rows 数组的下标（视觉顺序），不是 TvRowMeta.id。
// id 仅供行组件注册/注销时定位自己，模型内部一律用下标。
interface FocusPos { rowIndex: number; itemIndex: number; }

function moveFocus(rows: TvRowMeta[], current: FocusPos, dir: Direction): FocusPos;
```

`rows` 按视觉顺序排列。`moveFocus` 是纯函数，返回新坐标；调用方负责把坐标映射回元素并 `focus()`。

### 按键处理

`useTvKeys` 仅在 `isTvLike` 为真时挂载监听。四个方向键一律 `preventDefault()`，页面不再自行滚动——这同时修掉「滚不回最顶部」的问题。

### 滚动与遮挡

焦点元素调用 `scrollIntoView({ block: 'nearest', inline: 'center' })`；配合 CSS `scroll-margin-top` 让元素停在 sticky 顶栏下方，修掉顶栏遮挡问题。

### 边界情况

- 行末继续按右：停住，同时触发该行的「加载更多」回调
- 不做循环导航——遥控器上循环会让人失去方向感
- 行在加载中（length 为 0）时被上下移动跳过

## 第 1 步：电视首页

### 结构

顶栏一行（搜索 / 收藏 / 设置），其下每个豆瓣分类一行：为你推荐、热门、最新、豆瓣高分、冷门佳片、华语、欧美、韩国、日本。

### 组件

- `components/tv/TvHome.tsx` — 页面骨架，装配行
- `components/tv/TvRow.tsx` — 一行横向卡片，注册到焦点模型
- `components/tv/TvPosterCard.tsx` — 单张海报卡片，真实 `<button>`

### 尺寸（按 960 CSS px 画布）

一行约容纳 5–6 张海报。正文 16px CSS（物理 32px），3 米观看距离下合适。焦点环与间距按 960 的尺度给，不照搬桌面密度。

### 焦点视觉

选中卡片放大至 1.08、加环、露出标题；未选中的压暗。电视上焦点必须非常显眼。

### 行懒加载

9 行同时请求豆瓣会拖慢首屏，且豆瓣接口在 Cloudflare 上本就不稳。只有滚动到接近视野的行才发请求；未加载的行显示骨架占位，并被焦点模型识别为空行自动跳过。首屏只拉前 2–3 行。

## 测试策略

1. **单元测试** — `focus-model.ts` 是纯函数，用仓库现有的 `npm test`（`tsx --test`）覆盖：行长度不等、空行跳过、边界停住、换行保持列号
2. **浏览器验证** — 视口设为 960×540，用方向键实际走一遍焦点路径，确认无跳错
3. **手机回归** — 视口 375×812 确认走的仍是原组件，行为不变

## 风险

| 风险 | 应对 |
|---|---|
| 豆瓣接口在境外不稳，9 行请求放大问题 | 行懒加载，首屏只拉 2–3 行 |
| 误伤手机端 | 所有入口由 `isTvLike` 把守；测试含手机视口回归 |
| 焦点手感不符合预期 | 第 1 步完成后先在真机验收，确认后再做后续页面 |
| 上游同步产生冲突 | 改动集中在新增文件，对现有文件只加一行分支判断 |
